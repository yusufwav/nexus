## 2026-10-21 — The mobile app authenticates with a bearer token, and the server keeps one front door
**Agent:** backend
**Decision:** The server's Better Auth instance has the `bearer` plugin enabled (`plugins: [bearer(), nextCookies()]`), so the mobile app can present `Authorization: Bearer <session token>` and have it converted back into a session cookie server-side.
**Because:** React Native's `fetch` has no cookie jar, and the session cookie is `httpOnly` — a browser keeps cookies in a jar it manages, a native client holds the credential itself, and a header is the only shape that survives. The alternative was a second authentication path for native clients, which would have meant a second implementation of the session lookup, the refresh window, the seven-day expiry and the rate limiter. The plugin is a door, not a second front door: everything downstream is the same code path the website uses. The origin check still holds, because Better Auth's `validateOrigin` only runs on a request carrying a `Cookie` header — a bearer request carries no cookie to forge, and the token's HMAC signature is the credential.
**Costs:** A bearer token is the session token, so a stolen one is exactly as dangerous as a stolen cookie. That is why the session is short-lived and refreshed on use. `nextCookies()` must stay **last** in the plugin array — Better Auth warns when a cookie plugin is not final.
**Touches:** `packages/auth/src/index.ts` (uncommitted), and `src/lib/auth-client.ts` in the mobile repo, which carries **both** the bearer token and the session cookie so the app works against a server that does not have the plugin yet.

## 2026-10-21 — The mobile app sends an `Origin` header, and it is an assertion, not a bypass
**Agent:** backend
**Decision:** The mobile app sends `origin: <server url>` on every request, and the server keeps its `trustedOrigins` allowlist strict — no wildcard, no "trust whatever Origin the request carries".
**Because:** React Native's `fetch` sends `Origin: null`, which Better Auth's CSRF check reads as a missing origin and refuses with `MISSING_OR_NULL_ORIGIN`. Naming the server satisfies the check, and the check keeps doing its job: a third-party origin is still refused. A native app has no ambient cookies and no ambient session — it sends only what the app code tells it to send, and the token is in the device keychain — so a hostile website cannot make the app send anything at all. The header is an assertion about who the client is, and the server checks that assertion against the allowlist. The rejected alternative was the "trust the Origin header" fallback, which silently reduces the check to no check at all.
**Costs:** Every native client must name its server. A third-party native client cannot authenticate without being added to `trustedOrigins`.
**Touches:** `packages/auth/src/index.ts` (`trustedOrigins`), `src/lib/auth-client.ts` in the mobile repo.

## 2026-10-21 — `BETTER_AUTH_EXTRA_ORIGINS` is LAN-testing only, and warns loudly in production
**Agent:** backend
**Decision:** `BETTER_AUTH_EXTRA_ORIGINS` stays out of `apps/web/.env.schema` (so varlock never complains when it is absent), arrives through turbo's `globalEnv`, and prints a multi-line warning on every cold start when it is set with `NODE_ENV=production`.
**Because:** Listing an origin there lets a page on it make authenticated requests with the reader's session cookie — exactly what you want testing from a phone on the same wifi, and exactly what you do not want on a deployed site. It is a **loud warning rather than a hard failure** because throwing would break the one case it exists for: someone mid-development with the variable set locally, which is the opposite of helpful. Printing the origins on every cold start is enough that nobody can ship it without having seen it.
**Costs:** A production cold start logs four lines of warning if the variable is left set. That is the intended price of the check.
**Touches:** `packages/auth/src/index.ts`.

## 2026-10-21 — The status bar strip is the native window, so its colour is set at runtime
**Agent:** mobile
**Decision:** The strip where the reader sees the clock, battery and signal is coloured by `SystemUI.setBackgroundColorAsync` at runtime, from the active palette, to the header's flattened `surfaceRaised` — not by `app.json`'s `backgroundColor`.
**Because:** React Navigation's `statusBarTranslucent` and `statusBarBackgroundColor` look like the answer and are not: `react-native-screens` implements both as **no-ops on Android** (`override fun setStatusBarColor(view: Screen, value: Int?) = Unit`). On Android the strip belongs to the native window, whose colour is `android:windowBackground` — and that comes from `app.json`, which is a **build-time constant** that cannot follow a palette the reader picks at runtime. The app has 52 of them, so a hard-coded colour is wrong on 51. The rejected alternative was leaving it at a fixed black, which is what produced a black band above every light palette.
**Costs:** The window's colour is set in JavaScript, so it is the *default* palette's colour until the theme is known. `app.json` still sets `backgroundColor` for that window — it is what the reader sees during the splash screen. `expo-system-ui` must stay installed.
**Touches:** `src/components/NativeWindowBackground.tsx` (new), `src/app/_layout.tsx`, `app.json`, and `STYLING.md` §1.4a in the mobile repo.

## 2026-10-21 — A shared value is never written during a render
**Agent:** mobile
**Decision:** Animation state that a callback writes to lives in a ref (`useRef(useSharedValue(0))`), and the write happens outside React's render phase — the next value is computed from a ref, the shared value is written, and only then is `setState` called.
**Because:** Writing `shared.value = ...` inside a `setState` updater is a write during React's render phase, because React calls updater functions while rendering. Reanimated warns about it loudly and is right. On the web it is untidy; **on Android the animation silently never runs** — the worklet is scheduled against a value that is about to be torn down. The rejected alternative was writing the shared value first and deriving the state from it, which has the same problem in a different order.
**Costs:** None, once the refs are in place. The lint rules `react-hooks/exhaustive-deps` and the React Compiler's `immutability` rule **contradict each other** here — listing a shared value in a dependency array freezes it, and the compiler then refuses every write to it — so the refs satisfy both: a ref's `.current` is mutable by definition, the compiler does not freeze it, and `exhaustive-deps` knows a ref is stable.
**Touches:** `src/app/(tabs)/index.tsx`, `AGENTS.md` rule 7 in the mobile repo.

## 2026-10-21 — The glassmorphism and the WebView backgrounds are gone, and the page is flat
**Agent:** mobile
**Decision:** The app has one flat page colour (`theme.tokens.bg0`) and one flat panel colour (`theme.tokens.bg1`). The four live visual fields (gradient ASCII, horizon bloom, letter glitch, pixel blast) and the glassmorphism are removed, and `expo-blur` and `react-native-svg` are uninstalled.
**Because:** The glassmorphism had no workable implementation on this stack — `@callstack/liquid-glass` needs Xcode 26 and has no Expo config plugin, and `expo-glass-effect` is iOS 26+ only. The WebView fields had a second problem: `expo-blur`'s `BlurTargetView` is a native Android `ViewGroup` that reparents children into an inner `BlurTarget`, taking the DOM `DomWebView` out of RN's hierarchy, which broke with `Unable to find the class expo.modules.webview.DomWebView view with tag N`. The rejected alternative was keeping the fields and making the blur work, which would have meant a second rendering path for the background.
**Costs:** The app lost its live backgrounds. The panels are opaque `bg1` over a `bg0` page, with a grain tile and a hairline edge — the grain reads as a material on a small panel and as dirt on a large flat area, which is why it is on the container and nowhere else.
**Touches:** `src/components/dom/` (deleted), `src/components/ui/GlassPanel.tsx` (rewritten as an opaque card), `AGENTS.md` rule 2 in the mobile repo.

## 2026-10-21 — The mobile app's local SQLite store is the source of truth offline; the server is the source of truth for the account
**Agent:** mobile
**Decision:** The app keeps its notes, questions, progress and read positions in a local `expo-sqlite` database, and talks to the server only for sign-in, sign-out and session validation.
**Because:** The app must work without a connection, and the server holds the credentials. The rejected alternative was making the app read the server for content, which would mean the notes are unavailable on a train — and it is also the only arrangement in which `DATABASE_URL` never reaches the device, because a React Native bundle ships inside the `.apk` where anyone can read it.
**Costs:** Two representations of the library exist — the bundled `src/content/` and the server's `packages/db` tables — and they have to agree. The server's read budget and the app's local copy are separate mechanisms, and the app's copy is not rate-limited because it is already on the device.
**Touches:** `src/storage/database.ts`, `src/storage/library.ts`, `src/content/` in the mobile repo; `packages/db/src/schema/modules.ts` and `notes.ts` on the server.

## 2026-10-21 — The 4xx body is flat, and a 5xx body is never shown to the reader
**Agent:** backend
**Decision:** Auth failures answer `{ message, code }` at the top level — not nested under `error` — and a 5xx body is replaced server-side before it reaches the client.
**Because:** The `message` is written for the reader and is shown to them verbatim, so it has to be where the client expects it without the client having to know which shape the failure took. A 5xx body can carry internal detail — a driver error naming the database host and the port — and the mobile app must not be the only thing standing between that and a reader. The rejected alternative was a uniform error envelope, which would have meant either exposing 5xx detail or stripping 4xx detail, and both of those are worse.
**Costs:** Two error shapes to read rather than one. `GET /api/auth/get-session` also answers `200 null` for "not signed in" rather than a 404, which is a third shape the client must handle.
**Touches:** `packages/auth/src/index.ts`, and `src/lib/auth-client.ts` in the mobile repo, which is the contract.

## 2026-10-21 — An Android build from this path needs a real copy at a short, space-free path
**Agent:** mobile
**Decision:** Building for Android on Windows is done from a **real copy** of the project at a short, space-free path (e.g. `C:\n`), not from the working directory and not through a junction.
**Because:** CMake escapes a space as `$` when it writes the path into its build rules, and then creates a directory that is not the one it wrote — `ninja: error: mkdir(CMakeFiles/reanimated.dir/C_/Users/yusuf/orca/mobile_projects/Nexus/...): No such file or directory`. The path length matters too: Windows' limit is 260 characters and CMake's generated paths cross it. A **junction is not enough** — it resolves back to the real path, so the space comes back with it. `subst` was also tried and breaks the Expo settings plugin, which shells out to `cmd` against the substituted path.
**Costs:** A copy of the project per build, and `JAVA_HOME` has to be set — `sdkmanager` and `avdmanager` refuse to run without it, and Android Studio's bundled JBR is not on the PATH by default: `$env:JAVA_HOME = "C:\Program Files\Android\Android Studio\jbr"`.
**Touches:** `PORTING.md` §7a in the mobile repo.

## 2026-10-21 — The maths is typeset by the app, not by KaTeX
**Agent:** frontend
**Decision:** The tutor's LaTeX is parsed, laid out and drawn by the app — `src/lib/latex/` and `src/components/Math.tsx` — with no KaTeX, no WebView and no new dependency. The layout uses TeX's own box model (width, height above the baseline, depth below it) and every measurement is in em, computed arithmetically.
**Because:** React Native cannot lay maths out. There is no `View` inside a `<Text>`, and in the New Architecture a nested `<Text>` is a **span** — `TextProps` does not extend `ViewProps`, so it cannot be transformed or repositioned. A superscript cannot be raised inside a paragraph and a fraction cannot be built out of one, so something has to do the layout. The unlock is that the app's face is **monospace**: every glyph has the same advance, so a run of text has an exact width, a fraction's numerator can be centred on a rule that was never measured, and there is no `onTextLayout`, no second pass and nothing to get wrong on a device. The rejected alternatives were KaTeX in a WebView — a WebView per equation in a scrolling chat, and a web package in an all-native app — and giving up on real maths and rendering the source.
**Costs:** A LaTeX subset, not LaTeX. About forty constructs: groups, scripts, `\frac`, `\sqrt`, the big operators with their limits, `\left…\right`, the matrix environments, the symbol table, and the styled groups. An unknown command is kept as its literal text rather than swallowed, so nothing ever disappears. Delimiters can also be stretched only by making the glyph bigger, not longer.
**Touches:** `src/lib/latex/` (new), `src/components/Math.tsx` (new), `src/components/Markdown.tsx`, `src/theme/font-metrics.ts`, `scripts/generate-font-metrics.mjs`, `scripts/test-latex.ts`, `scripts/preview-latex.mjs`, `STYLING.md` §1.6 and `PORTING.md` §6d in the mobile repo.

## 2026-10-21 — The font's repertoire is checked at build time, and every missing glyph has a fallback
**Agent:** frontend
**Decision:** `scripts/generate-font-metrics.mjs` reads the TTF files and writes both the metrics and **the characters the font cannot draw**. Every LaTeX command that needs one of those characters carries a documented fallback, chosen to keep the meaning: `\cdot` → `·`, `\iint` → `∫∫`, `\sqrt[3]{x}` → `√` with a raised 3, `\hbar` → an `h` with a bar drawn over it.
**Because:** A character the font does not have comes out as a **box**, and a page of boxes is worse than a page of plain text. The check is at build time because the alternative is discovering it on a phone. It found fifteen: `⋅ ∝ ∖ ∠ ∗ ∬ ∭ ∮ ∯ ∰ ⨁ ⨂ ∛ ℏ ℜ ℑ`. The rejected alternative was trusting the font, which is how a renderer ends up shipping tofu.
**Costs:** The repertoire is a fact about the font files, so a font change silently invalidates the fallbacks. The test asserts that no expression the engine can parse produces an undrawable character, which is what catches it.
**Touches:** `scripts/generate-font-metrics.mjs`, `src/theme/font-metrics.ts`, `src/lib/latex/symbols.ts`, `src/lib/latex/metrics.ts`, `scripts/test-latex.ts`.

## 2026-10-21 — A `$` span that does not look like maths is a dollar sign
**Agent:** frontend
**Decision:** The splitter that finds maths in a line refuses a `$` span that is closed but does not look like maths — a bare number, a span with a space at either end, a span that is not closed on the same line. A refused `$` stays a literal dollar sign and the text around it is left alone.
**Because:** `$` opens inline maths, so a price written `$50` opens a formula that never closes, and everything after it gets swallowed into the maths. The web app solves this by asking the model not to write currency that way, which is a rule about the MODEL; this is the same rule enforced in the renderer, so it holds even when the model breaks it. The rejected alternative was trusting the prompt, which fails silently and looks like a rendering bug.
**Costs:** A span of maths that happens to be a bare number is rendered as text. That is the intended trade — a price is more common in a study partner's answer than a one-digit equation.
**Touches:** `src/lib/latex/index.ts`, `src/lib/latex/parse.ts`, `scripts/test-latex.ts`.

## 2026-10-21 — The page name lives in the header, and only in the header
**Agent:** frontend
**Decision:** Every screen's body opened with a line that named the page — an eyebrow (`CATALOGUE`, `PRACTICE`, `ABOUT`) or, on two screens, a headline that was the header's title verbatim (`You`, `Model provider`). All of them are gone. The body now opens with the headline that says something the header does not.
**Because:** `ScreenHeader` was introduced to be the one place a screen is named, and it owns the top safe-area inset as well. A page that says its name again a few pixels lower is saying it twice, and the second statement is always the weaker one — the header's is the real title bar. The rejected alternative was leaving the eyebrow and calling it "a section label", which is what it was on the pages where the header did not already say it.
**Costs:** Two pages — the profile and the provider — now open with their lead paragraph rather than a headline, because their headline WAS the page name.
**Touches:** ten screens under `src/app/`, and the imports and style entries that the removal left unused.

## 2026-10-21 — A picker can group its options, so a list of lists is a list of lists
**Agent:** frontend
**Decision:** `Select` takes an optional list of GROUPS as well as a flat list of options. A group's heading opens to show what is under it, and the heading is what the reader sees when the group is closed. The tutor's model picker uses it: a group is a provider, and a provider's models collapse into the provider's name until it is opened.
**Because:** The models a reader can choose come from several providers, and a flat list of them loses where each one came from — two providers list the same model id, so the tick lands on two rows and a choice cannot be qualified. The rejected alternatives were a flat list with the provider in each row's detail line (which is the same list, only noisier) and a separate picker per provider (which is two dropdowns where the reader has to know which one to open).
**Costs:** The groups are a second mode for one component, so `Select` carries two ways of listing things. The tutor also has to keep each provider's models in a cache and fetch them when a heading is opened, because asking every provider at once is a request per provider for a list the reader may never look at.
**Touches:** `src/components/ui.tsx` (`Select`, `SelectGroup`), `src/app/(tabs)/tutor.tsx`, `src/lib/model-picker.ts` (new), `src/components/icons.tsx` (`chevronDown`), `scripts/preview-picker.mjs` (new).

## 2026-10-22 — A button's place is one of four, and a button is never restyled to move it
**Agent:** frontend
**Decision:** Every button in the app sits in one of four arrangements: an action on a row or an item goes on that row at the trailing edge; the only action of a block, a card or a screen is centred; a pair of alternatives goes in a row rather than a stack; and a button that continues a flow stays under the thing it continues. Moving a button never changes its variant, size, colour or label.
**Because:** A button's position is part of what it says. A lone action against the left gutter reads as a caption to the paragraph above it rather than as the thing to do, and a stacked pair of alternatives reads as a sequence of steps. The rejected alternative was restyling buttons while moving them, which quietly changes the app's hierarchy every time a button is touched.
**Costs:** Two React Native details have to be handled at every call site, and both are silent when they are wrong. A button brings its own `alignSelf: "flex-start"`, which in a **column** is the horizontal axis — so a button that should be centred has to say `alignSelf: "center"` explicitly, and in a **row** it has to say so as well or it sits at the top of the row rather than in the middle of it. And `fullWidth` asks the button to stretch to the width of the **block that holds it**, so a block that is `alignSelf: "flex-start"` makes the prop do nothing; where the button should keep the width of its own label, the block is made full width and the button's own `alignSelf` is overridden.
**Touches:** every screen under `src/app/`, and `STYLING.md` §1.3b in the mobile repo. The one shared primitive involved is `Button` in `src/components/ui/Button.tsx`, whose `alignSelf` default is what every one of those call sites has to override. `scripts/preview-buttons.mjs` (new) draws the before and after of three of them, so the placement can be **looked at** rather than assumed — it reads the type scale, the radius scale, the button metrics, the card padding and the gaps out of the source, so the drawing cannot drift away from the app.

## 2026-10-22 — The gradient ASCII field is back, as a DOM component, and its strength and its fade are the shader's own numbers
**Agent:** frontend
**Decision:** The web app's gradient ASCII field is ported into the app as a `'use dom'` component (`src/components/dom/GradientAscii.tsx`) and mounted as the FIRST CHILD of every screen's root, except **You** and **Provider**. The shape is `rise` — the field comes up from the bottom. The colours are the active palette's `bg0` and `accentA`, handed across the bridge as two strings, and the same four-stop ramp is derived from them. The field is at 60% (90% on the tutor), and the tutor's slow fade to nothing once the reader has sent a message is **the composite's own scale walking down inside the WebView**, not the opacity of the native view that holds it.
**Because:** The field is the web app's own WebGL2 pipeline, and a pipeline that has been looked at is worth more than a shader that has been rewritten — so it is a port, not a reimplementation, and the four changes are the four that had to be: the shape, the colours, the pointer (there is nothing under the reader's thumb to scramble, so the pointer is gone) and the font (the app's JetBrains Mono is a NATIVE font, and a native font is not a font the WebView can rasterise, so the ramp is drawn in the platform's monospace). The strength and the fade are in the shader because **a WebView is drawn into its own layer on Android, and a layer does not take the alpha of the view it is in**: a fade done on the native side is a fade that silently does not happen, on the platform where it matters most. The field is at 60% as a single scale applied last, so the wash, the glyphs and the halo all come down together — the field at 60% is the same field at 60%, not a field at 100% under a grey veil. The rejected alternatives were a native reimplementation of the pipeline in a different graphics API, and keeping the web app's `horizon` shape, which puts a wide band across the middle of the screen — exactly where the content is.
**Costs:** A WebView per screen, and the props cannot be captured by the effect that owns the GL context — a second mount would be handed a context the first one's cleanup already released — so the props live in a ref and the repaint reads them from there, or the field repaints the palette it booted with and the reader's theme change changes the page and not the field. The light palettes need ink rather than white glyphs, which is the reference engine's branch and not the web app's. The composer's placeholder on the tutor sits over the brightest part of the field until the reader sends a message, which is the trade the 90% asked for.
**Touches:** `src/components/dom/GradientAscii.tsx` (new), `src/components/GradientAsciiBackground.tsx` (new), thirteen screens under `src/app/`, `STYLING.md` §1.7, `PORTING.md` §2 and §2a, `AGENTS.md` rule 2 in the mobile repo.

## 2026-10-23 — The field is one WebView for the whole app, one colour, and alive
**Agent:** frontend
**Decision:** The gradient ASCII field is mounted ONCE, above the navigator, rather than once per screen; every screen is transparent so it shows through them, except **You** and **Provider**, which keep their flat `bg0` and no field. The ramp is ONE colour — the palette's own accent at its own saturation, at every stop — and the field is the reference engine's own numbers (flow, speed, density, glyph alpha, gradient, glow, flicker, depth, softness) with the grain at zero. The shape reaches the bottom two thirds of the screen, in proportion to the screen. The tutor still claims ninety per cent and still fades away over 2.6 seconds once the reader has sent a message, and a screen now claims a strength through a context rather than owning a field.
**Because:** A field that reloads with every screen is not a background, it is a flash — every screen was its own WebView, so every screen paid for a WebView booting, four shaders compiling and a 2.4 second intro wiping in, and the reader saw the flat page colour for all of it. One field is painted once and stays painted. The ramp was four lightnesses of the accent, which meant the field changed colour as it climbed and read as a wash of two colours; one colour with a ramp of ALPHA is the same picture without the second colour in it, and what carries the field up the screen is its density. The grain resampled at 24Hz and read as a rendering fault rather than as a texture, and the reference's own control panel reads zero. The flow and speed were turned up from the reference's because the reference's field is a four-colour ramp, where a character that changes COLOUR is a change you see at a glance; with one colour the characters themselves are the only movement left, and they need more of it to read.
**Costs:** The screens' roots are transparent, and so are the navigation theme's `background` and the tabs' `sceneStyle` — an opaque one anywhere in that chain is a lid over the field, and the field is invisible behind it rather than wrong. The context's provider has to wrap the navigator as well as the field, because the screens are the field's SIBLINGS and a sibling cannot reach a provider inside the field. A screen that wants a different strength claims it while it is focused and gives it back when it is not, so a screen change is a strength that WALKS to its new value over three quarters of a second rather than a jump. The tutor's composer has no panel behind it — the field is behind it, and the hairline it would have had is invisible against a lit field — so the typed text takes its colour from the same side the field does: the page's own black over the lit field of a dark screen, the page's own white over the pale field of a light one.
**Touches:** `src/components/dom/GradientAscii.tsx` (the SPEC, the ramp, the shape, the tone's alpha ramp, the strength and the fade), `src/components/GradientAsciiBackground.tsx` (one field, and the claim), `src/app/_layout.tsx`, `src/app/(tabs)/_layout.tsx`, every screen under `src/app/` that used to have a field of its own, `src/app/(tabs)/tutor.tsx` (the claim, and the typed text's colour), `STYLING.md` §1.7, `PORTING.md` §2a, `AGENTS.md` rule 2 in the mobile repo.

## 2026-10-23 — The field does not follow the app's "Reduced motion" switch
**Agent:** frontend
**Decision:** The gradient ASCII field is not wired to the app's "Reduced motion" switch. That switch says what it does — "Calms the side menu's slide" — and the field is not the side menu. The field's ambient motion always runs.
**Because:** The switch froze the field DEAD on any device that had it on, and the symptom was confusing enough to cost an hour: the intro played perfectly, and after that nothing moved at all — no flicker, no characters changing, no drift. The reason is in the frame loop: the ambient clocks advance only when the motion is not reduced, while the intro's clock advances UNCONDITIONALLY. So a field that was "reduced" still wiped itself in and then sat there like a photograph, and the reader could not tell a frozen field from a broken one. The field is the one thing in the app that is allowed to be alive, and a switch that is documented as being about a drawer has no business turning it off.
**Costs:** The field does not honour a reduce-motion preference of any kind, because the app has only this one and it is the drawer's. The DOM component still takes a `reduced` prop for a caller that has a preference of its own, and this caller does not pass it. If the app ever grows a real reduce-motion setting, the field is the thing it has to decide about: a field that stops moving is a field that is a picture, and that is a different decision from calming a drawer.
**Touches:** `src/components/GradientAsciiBackground.tsx`, `src/components/dom/GradientAscii.tsx` (the SPEC's motion numbers, the shape's own clocks, the drift of the domain warp and the tick of the characters), `STYLING.md` §1.7, `AGENTS.md` rule 2 in the mobile repo.

## 2026-10-24 — A screen change is a CUT, because a transparent screen cannot animate over another
**Agent:** frontend
**Decision:** Both navigators set `animation: "none"` — the root stack in `src/app/_layout.tsx` and the tabs in `src/app/(tabs)/_layout.tsx` — so a screen change replaces the screen in one frame. The login screen's own `animation: "fade"` is gone with it.
**Because:** The screens are transparent on purpose: there is one gradient ASCII field for the whole app, mounted behind the navigator, and an opaque screen is a lid over it. A native transition cannot cope with that. Android's default is a 450ms slide-and-fade in which the incoming screen and the outgoing one are drawn **in the same frame**, and the old fragment is only destroyed when the animation ends — so for half a second both screens' headers and both screens' text are visible, with the incoming screen acting as a window onto the old one. That is the bug the reader reports as "both screens are loaded at the same time before the old one can unload". No opacity or duration fixes it: any animation that draws both screens at once is a double exposure when the top one is see-through, and `fade` (a native cross-fade) is the worst of them. The rejected alternative was a JS fade of the incoming screen after an instant swap — it trades a ghost for a flash of the field through the two screens that are meant to be opaque, and on a back-navigation the screen is already painted before a fade could start, so it pops. With the cut, the FIELD carries the continuity: it never moves, never reloads and never fades, so the room stays and the page changes.
**Costs:** No slide, no fade, no shared-element feel on any navigation; a push reads as a terminal refresh rather than as a page arriving. The drawer covers most drawer-driven navigations anyway, because its close animation (320ms) is still running when the screen has already changed underneath it.
**Touches:** `src/app/_layout.tsx`, `src/app/(tabs)/_layout.tsx`, `STYLING.md` §1.7, `PORTING.md` §2a, `AGENTS.md` rule 2 in the mobile repo.

## 2026-10-24 — The README container is a panel, not a window: it has no bar of its own
**Agent:** frontend
**Decision:** `src/components/ui/TerminalPanel.tsx` is deleted and the home screen's README container is a plain `GlassPanel`. The bar it used to carry — three dots on a `surfaceRaised` strip over a hairline — is gone, and `ScreenHeader` is the only bar in the app.
**Because:** The bar was the README container's own chrome when it was the only thing at the top of the screen, and it moved to the top of the screen as `ScreenHeader`. What was left was a second terminal window drawn ten points under the first: two rows of dots, two hairlines and two raised surfaces with nothing between them, which reads as a rendering mistake rather than as depth. The container keeps everything that makes it a container — the opaque `bg1`, the grain, the hairline edge, `RADIUS.panel` and the 22-point body padding — and those are exactly `GlassPanel`'s defaults, so keeping a separate component for it would have been a second name for the one container. The rejected alternative was a `chrome={false}` prop on `TerminalPanel`: a component with one call site and one setting is a file to keep in sync for no reason.
**Costs:** The app loses the "this is a file in a window" metaphor on the home screen; the header carries it instead. `scripts/preview-readme.mjs` was rewritten to draw the header and the bar-less panel, which is what the reader sees now.
**Touches:** `src/components/ui/TerminalPanel.tsx` (deleted), `src/app/(tabs)/index.tsx`, `src/components/ui/ScreenHeader.tsx` (the doc comment and the dot comments), `src/theme/radius.ts` (a comment), `scripts/preview-readme.mjs`, `STYLING.md` §1.2/§1.3a/§1.4/§1.4b/§8, `PORTING.md` §2, `orchestrator/project-context.md` §11.2.
